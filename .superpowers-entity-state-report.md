   `MapWireValue(int raw) : ActorState` mapping (9→Dead, 23→Breaking, else→Unknown). Mirrors the
   `DungeonRunIdGate` precedent: a pure, no-BepInEx/Unity-dependency static mapper directly unit-tested
   from `Stellar.Application.Tests` via the existing `Stellar.Infrastructure` → `Stellar.Application.Tests`
   `InternalsVisibleTo` grant.

4. **`Stellar.Infrastructure.Game.PandaEntityStateProbe`** (new, + `.Diagnostics.cs` partial) — the
   Harmony patch. See "Patch resolution strategy" below.

5. **Host wiring** (`Wiring.Wire.cs` — `HookEntityStateSignals`, called from `BootstrapPlugin.ApplyLifecyclePatches`
   right after `HookGameLifecycleMethods`, i.e. once per boot, after all 8 hot-update assemblies are
   confirmed loaded). Constructs `PandaEntityStateProbe(typeRegistry, _combatService!, _combatService!, log)`
   — `CombatService` already implements both `ICombatEventSink` (event sink) and `ICombatSnapshot`
   (`ServerNowMs`, for the timestamp — same pattern `PandaDungeonProbe` already uses) — and calls
   `.Install(hooker)`, reusing the SAME shared `HarmonyGameMethodHooker` instance the lifecycle patches
   use (same Harmony id, no new Harmony instance). Host stays thin: construction + one `.Install()` call,
   no logic.

6. **Diagnostics** (`PandaEntityStateProbe.Diagnostics.cs`) — first 10 observations of `Dead` and first 10

7. **`FrameworkVersion`** bumped `1.16.1` → `1.17.0`, changelog paragraph added in the doc-comment

## Patch resolution strategy + soft-fail behaviour

Confirmed via `python3.10 tools/dump-types.py` against `recon/cpp2il-out/Panda.Script.dll`
(dated 2026-07-21, current release_3.7 — see "Concerns" for currency caveat) plus a scratch script
decoding the raw field/method signature blobs (not just names) to nail down exact types:

- `Panda.ZGame.EntityCtrlDead` (← `EntityCtrlBase` ← `StateCtrlBase`) declares its OWN `OnEnter`
  (confirmed a real override, not inherited) — this is the concrete type the spec says to patch, not the
  virtual base.
- `Panda.ZGame.ZStateBreaking` (← `ZState`) likewise declares its OWN `OnEnter`.
- **Both** `StateCtrlBase.get_Host` and `ZState.get_Host` return `Panda.ZGame.ZEntity` (decoded the
  signature blob token — both resolve to TypeDef row 4758, `Panda.ZGame.ZEntity`). So one host-resolution
  shape (`type.GetProperty("Host", instanceFlags)?.GetGetMethod(nonPublic:true)`) covers both patch sites,
  despite them not sharing a common state base class.
- `Panda.ZGame.ZEntity.Uuid` is backed by an `Int64` field (`<Uuid>k__BackingField`, sig `0x0a` =
  `ELEMENT_TYPE_I8`) — exactly `EntityId`'s underlying type.
- Both `OnEnter` methods have signature `void OnEnter(Zproto.EActorState)` (HASTHIS, 1 param, retTyped
  void, param TypeRef → `Zproto.EActorState`) — confirms the argument is a real enum, used defensively
  (see below).

**Install()** (`PandaEntityStateProbe.Install`, called once from Host after hot-update-ready) resolves
`Panda.ZGame.ZEntity` + its `Uuid` getter first; if either is missing, the WHOLE feature logs a warning
and turns off (no `EntityId` can be built without it). Otherwise it resolves the `Dead` and `Breaking`
sites **independently** — each missing type/accessor logs a warning and disables ONLY that one signal,
never throws, never blocks the other site or the rest of boot. This mirrors `HotkeyKeyBlockPatch` /
`PandaWorldAttrProbe`'s soft-fail idiom exactly.

**The postfix (`TryRaise`)** reads `Host` off the state instance that JUST executed `OnEnter` —
synchronous, same call frame, not a later poll of an arbitrary id — so per `docs/il2cpp-probing-safety.md`
this is NOT the TOCTOU live-object class that native-AVs (the object is provably alive; the game's own
call stack is executing a method on it right now). It's the same shape of read `HotkeyKeyBlockPatch`,
`PandaChatProbe`, and `WorldNtfStubDispatcher` already do on Harmony postfixes.

**`ResolveState`** prefers the game's own `EActorState` argument (`args[0]`, unboxed via `Convert.ToInt32`
and run through `ActorStateMapper.MapWireValue`) as a cross-check that costs nothing when it agrees;
if that unbox/map fails or returns `Unknown` for ANY reason (unexpected interop boxing shape, future game
change), it falls back to the literal `ActorState` implied by WHICH concrete `OnEnter` fired — a fact that
is already conclusive by construction (`EntityCtrlDead.OnEnter` only ever means `Dead`). So the primary
signal never depends on successfully unboxing the argument; the argument is pure bonus verification.

Any exception anywhere in `TryRaise` is caught and swallowed (logged only under `StellarDiagnostics`,
to avoid turning a per-transition reflection hiccup into log spam); `HarmonyGameMethodHooker.Trampoline`
also catches everything as a second line of defense, so nothing can propagate back into the IL2CPP
trampoline.

## Concerns / honest caveats

- The Cpp2IL dump used (`recon/cpp2il-out/Panda.Script.dll`) is dated 2026-07-21; today is 2026-07-28.
  I did not re-run a full `/recon` (that's a broader checklist) — I only ran targeted, read-only
  `dump-types.py` queries against the existing dump. If the game patched between 2026-07-21 and now,
  the exact member shapes should be re-confirmed; the code's soft-fail-per-site design means a shape
  change degrades to "that signal is off" (logged) rather than a crash or silent wrong data, but it would
  still miss the signal until the recon is refreshed.
- I chose to make the Harmony postfix ALSO read/map `args[0]` (the game's own `EActorState` value) as a
  cross-check, rather than purely hardcoding `Dead`/`Breaking` per patch site. This was a judgment call:
  it gives the tested `ActorStateMapper` a genuine (if defensive/secondary) production code path instead
  of being disconnected logic that only exists to have something to test. If this is considered
  over-engineering for a signal that's already unambiguous by construction (which concrete `OnEnter`
  fired), the fallback-to-literal path means removing the `args[0]` read entirely would be a small,
  safe simplification — flagging it explicitly rather than silently deciding either way.
- No in-game verification was attempted (per instructions) — this is committed-only work on a local
  branch, not deployed, not built into a bundle, not tested against a running game.

## Review round 1 — fixes (2026-07-28)

Review verdict: "Needs fixes" — architecture/layering/soft-fail chain/patch-site resolution
independently verified correct; one Important finding blocked deploy, plus three Minors.

### Important — ungated log budget was session-lifetime, not per-run

**The bug:** `FirstObservedLogCap = 10` was a single counter incremented on ANY entity's `Dead`
observation, for the life of the process, never reset. Spec § 4's whole point is that the owner's
**next** raid answers the scripted-kill question from one log line with no scheduled test. Ten
ordinary mob deaths happen within minutes of normal play, so by the time a raid starts — possibly
an hour into the session, after unrelated dungeons/leveling — the budget was already silently
spent, and the only remaining path was the `STELLAR_DIAGNOSTICS`-gated line, which needs an env
var AND a restart set up BEFORE the raid: exactly the scheduled test the design exists to avoid.
The `DamageLogCap` precedent this was modelled on is a different job (a boot-time "is the wire
live" check for an event firing many times a second, where burning the cap in seconds is
harmless) — deaths are orders of magnitude rarer, so the same shape was wrong here.

**Fix chosen:** per-scene reset (the reviewer's first, "cheapest, directly matches the goal"
option), not the boss-tag-filter or uncapped options. `PandaEntityStateProbe.ResetObservationBudget()`
(new public method) zeroes both per-kind counters AND their cap-reached latches; called from
`BootstrapPlugin.OnEnterScene` (`Wiring.GameLoop.cs`) — the SAME lifecycle hook that already
resets other probes' state on a new scene (e.g. `_inventoryProbe!.OnLifecycleAdvanced()` right
next to it). Every dungeon/raid instance — including one entered an hour into a session, after
budget-spending trash content earlier — gets its own fresh 10-per-kind allowance the moment its
scene loads. I did not add boss-tag filtering (`GetMonsterByEntity(...).IsBoss`): the reviewer
gated that option on the lookup being "safe and cheap at that call site", and the per-scene reset
alone already satisfies the stated goal without that extra dependency/risk, so I didn't chase it.

**One line on behaviour for a raid an hour into a session:** whatever the counters were at from
earlier content, `OnEnterScene` for the raid's own instance zeroes them, so the raid gets a full,
fresh 10-observation allowance for `Dead` and 10 for `Breaking`, regardless of how much unrelated
play happened earlier in the same process.

**Also fixed — cap-reached is now logged, ungated, once per scene per kind:**
`LogFirstObservedOrCapReached` logs `"[EntityState] Dead observation budget spent for this scene
(10 logged); further observations are silent unless StellarDiagnostics is enabled. Resets on the
next scene/dungeon entry."` the moment the 11th observation would have been silent — so silence
is never ambiguous; a raid that manages to exhaust the (now per-scene) budget still gets a plain
log line explaining why nothing more is printing.

### Minor 1 — `Install()` now wrapped in try/catch

`Install()`'s body (renamed to `InstallCore`) is now called from inside a try/catch in `Install()`
itself. Rationale in the code comment: it runs synchronously inside
`AppDomainHotUpdateWatcher.Observe`'s `AssemblyLoad` event handler, which has no surrounding
try/catch anywhere up its call chain (`OnHotUpdateReady` → `ApplyLifecyclePatches` →
`HookEntityStateSignals` → `Install`), and `GetProperty(name, flags)` can throw
`AmbiguousMatchException`. On any exception, logs a warning and disables the whole feature —
consistent with every other resolution path in this file, which was already null-safe; this
closes the one gap that wasn't.

### Minor 2 — recon note filed

`recon/entity-state-death-signal-notes.md` (superproject-level `recon/` — this is where the
Cpp2IL dump and every other `*-notes.md` file actually live; the framework submodule has no
`recon/` directory of its own). Documents: the `EntityCtrlDead` vs. `ZStateDead` choice and why
(controller-hierarchy "IS dead" vs. animation-hierarchy "PLAY dead", narrower surface), the
signature-blob-decoded confirmation that both `StateCtrlBase.get_Host` and `ZState.get_Host`
independently resolve to `Panda.ZGame.ZEntity` (same TypeDef row, different base-class chains),

### Minor 3 — `EntityStateChanged` parameter renamed

`CombatEvent.EntityStateChanged(long TimestampMs, EntityId EntityId, ActorState State)` →
`EntityStateChanged(long TimestampMs, EntityId TargetId, ActorState State)`, matching the
`TargetId`/`SourceId`/`SummonerId` convention of its siblings in the same file instead of
colliding with its own type name. Checked for property-access call sites (`.EntityId`) across
`src/`+`tests/` — none exist yet (only positional construction), so this was a zero-risk rename
pre-release.

### `args[0]` cross-check — kept

The reviewer floated dropping `ResolveState`'s read of the game's own `EActorState` argument as a
simplification. I kept it: it's genuinely exercised by `ActorStateMapper` (not disconnected test
theatre), degrades gracefully to the patch-site literal on any unbox/map failure, and the recon
note's signature-blob confirmation that the argument really is `Zproto.EActorState` (not an opaque
int) makes the read's cost/risk low relative to the corroboration it buys. Flagging this decision
explicitly rather than silently picking a side.

## Round 3 — field result: silent no-op, rework to machine-level hooks (2026-07-28)

**Field report:** owner's session confirmed framework 1.17.0 loaded, `ApplyLifecyclePatches` ran
(9 lifecycle patch lines logged), both patches installed cleanly (no soft-fail warning — the
types/members resolved exactly as round 1/2 predicted). The owner cleared three dungeons with mob
kills and three `stage` archives. **Zero `[EntityState]` lines.** `EntityCtrlDead.OnEnter` and
`ZStateBreaking.OnEnter` are real, correctly-resolved patches on real types — they simply are not
what runs when a monster dies on this build. This is exactly the failure class
`docs/il2cpp-probing-safety.md`'s "verify by instrumenting, not reasoning" principle warns about:
static evidence (the type exists, the member resolves, the shape matches the spec) is necessary but
not sufficient — only a real run proves the CODE PATH is actually exercised, and this one wasn't.

**Rework:** hook the state machine itself, not a leaf state — `Panda.ZGame.ZStateMachine.onStateChanged`
(primary — fires on every transition with both `fromState`/`toState`) and `.EnterState` (secondary —
fires with `targetState`). Both confirmed via fresh signature-blob decode
(`recon/entity-state-death-signal-notes.md` § "Round 2"): `onStateChanged(EActorState, EActorState) : void`,
`EnterState(EActorState) : void`, `get_Host() : ZEntity` (same TypeDef row as `StateCtrlBase`/`ZState`'s
`get_Host` — a third independent auto-property that happens to agree on shape). Also added
`ZStateDead.OnEnter` (the spec's named leaf alternative, absent from round 1's build entirely) and
kept `EntityCtrlDead.OnEnter` / `ZStateBreaking.OnEnter` installed as an explicit diagnostic — per
the coordinator's instruction, to learn whether either EVER fires for anything, now that we know
they don't fire for an ordinary kill.

**Corrected a latent round-1/2 bug while reworking:** `EntityCtrlDead.OnEnter(fromState)` /
`ZStateDead.OnEnter(lastState)`'s single argument is the state being LEFT, not entered — confirmed
by the coordinator's naming (`fromState`) and independently by `ZStateDead`'s own `lastState`
parameter name. Round 1/2's `ResolveState` read this argument as a defensive "cross-check of the
current state", which was silently wrong in principle (never manifested in the field only because
these leaf sites never fired at all). Round 3 removes that read entirely on the leaf sites — they
now hardcode the `ActorState` implied by WHICH concrete `OnEnter` fired (unambiguous by
construction) — and moves `ActorStateMapper` to where it's actually correct: filtering the machine
hooks' `toState`/`targetState` argument, which genuinely IS the state being entered.

**Hot-path discipline.** `onStateChanged`/`EnterState` fire for every actor's every transition
(movement, jumps, skills), not just death/break — orders of magnitude hotter than a death leaf.
`OnMachineStateChanged`/`OnMachineEnterState` unbox the state argument via `Convert.ToInt32` (a BCL
numeric conversion — dispatches through the boxed value's built-in `IConvertible`, NOT
`MethodInfo`/`PropertyInfo` reflection) and run it through `ActorStateMapper.MapWireValue` FIRST;
only a Dead/Breaking match reaches `RaiseIfHostResolves`, which is the only place either reflected
getter (`get_Host`, `get_Uuid`) is invoked. No reflected getter runs before the filter passes, on
either machine hook, for any transition that isn't Dead/Breaking — i.e. the overwhelming majority
of calls on a live raid.

**Two new instruments (both ungated, both per-scene-capped, both cleared by the existing
`ResetObservationBudget`/`OnEnterScene` hook):**
1. **Site attribution** — every `[EntityState]` observation line now reads
   `site=<onStateChanged|EnterState|ZStateDead|EntityCtrlDead|ZStateBreaking> entity=<id> entered <Dead|Breaking>`,
   so one run shows exactly which site(s) produced the signal.
2. **Unfiltered raw-transition proof** — `[EntityStateRaw] site=<onStateChanged|EnterState> from=<int|?> to=<int>`,
   the first 12 transitions per scene per machine site, logged REGARDLESS of whether they match
   Dead/Breaking. This turns "the runtime enum really is 9=Dead/23=Breaking" from an assumption
   (which is exactly what failed silently this round, in spirit — a value 9/23 mismatch would have
   looked identical to "the hook never fires") into a fact the log states outright. Both new
   instruments' per-scene caps log a "budget spent" line, ungated, once, when reached — same
   ambiguity-proofing as the existing observation-cap fix from round 2.

**De-duplication.** Up to five sites can now independently observe what might be the SAME real
transition (a controller-side entry and a machine-side one for the same death, or `onStateChanged`
and `EnterState` both firing for one transition). `ShouldRaise` keys on `(entity uuid, ActorState)`
with a 500ms wall-clock (`Environment.TickCount64`, not `ServerNowMs`) window, checked only AFTER a
site has already resolved host+uuid (never on the hot per-transition path) — a genuine duplicate
inside the window is suppressed (logged only under `StellarDiagnostics`, not one of the two ungated
instruments above — duplicates are informative but not what this round's instrumentation was
specifically asked to prove) and the map is cleared alongside the rest of the per-scene budget.
**Residual risk, stated plainly:** if two sites for the SAME real transition fire more than 500ms
apart (plausible if they belong to genuinely different underlying game systems that don't update in
lockstep), both would be raised — the window is a pragmatic bound for this diagnostic round, not a
provably complete guarantee, and the coordinator's own framing ("your call... we will drop whichever
proves redundant after one run") anticipates refining this once field data narrows it to one
raiser.

**What this round does NOT change:** the `ActorState`/`CombatEvent.EntityStateChanged` public
surface (still `TargetId`, still the same two named values), the per-scene reset mechanism itself
(reused as-is), `Install()`'s try/catch, or any layer/architecture rule.
